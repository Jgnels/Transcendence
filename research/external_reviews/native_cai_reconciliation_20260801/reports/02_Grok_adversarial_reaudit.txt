2. Sunk-cost attack (assume v0.2E–H never existed)
Knowing current 8.1.x CAI, DeepWar, Hecleas, Incata-style task tuning, SFO CAI surface, and available scripting/DB:

Evaluator/research use: Yes, I would still build a lightweight observer-safe challenge/portfolio/assignment evaluator today. The native system is still hard to score fairly and longitudinally. A pure metric harness that measures coherent-rival persistence, recovery mishandling, thrashing, and overcommitment has clear value and low risk.
Actual campaign decision-making: No. I would not build a full parallel strategic stack intended to select the tasks the game should pursue. I would start with native CAI + aggressive, measured DB/script influence (personality, budgets, task-generator priorities, the new 8.1 prioritization surface if exposed) under controlled ablations, and only escalate to a parallel planner if native + tuning failed specific, pre-registered fairness and late-game metrics.
Live action control: Definitely not. Control remains the highest-risk surface; I would keep it gated far downstream.

This differs from the first audit’s implicit recommendation. The first audit treated the parallel planner as the default architecture; under a clean-slate view the default becomes native executor + evaluator/tuner, with parallel ownership as a contingency.

5. Falsifying “native CAI is opaque, therefore we need our own planner”
Opaqueness is real but incomplete. Reconstructible or experimentally inferable surfaces include:

Task-generator groups and junctions (edited by every major AI mod; visible in RPFM).
Personality sets and their associated variables/budgets.
Budget and income allocation tables.
Strategic components.
Faction potential.
Distance/time scaling parameters (publicly described and changed in betas).
The new turn-dependent prioritization mechanism (at least the behavioral effect is public; schema exposure is UNVERIFIED).
Strength evaluation inputs (units, experience, bonuses, stances).
Campaign outcomes under controlled ablations of the above.

Strongest alternative architecture: Transcendence as instrumentation + evaluator + native-tuning system.

Observer packs remain for clean, path-free snapshots.
Offline evaluator (current v0.2E-style metrics + longitudinal churn/recovery/overcommit scores) scores native behavior.
Controlled DB/script influence layer (personalities, budgets, task-generator priorities, 8.1 prioritization surface if exposed) under hash-bound profiles.
Bounded correction only when evaluator detects a clear, pre-registered failure mode that native tuning cannot fix.
No project-owned task selection or force assignment in the application path unless the evaluator repeatedly falsifies the tuned native system on the registered metrics.

This removes the need to own strategic task selection while preserving fairness, explainability, and SFO compatibility.

7. Native force allocation vs v0.2G
Best available evidence (CA BETA blogs):
task generation → priority modification (distance/time, now also turn-progress) → strength evaluation on target → search owned forces for acceptable strength ratio → if none, recruit → execution.
Native advantages the project currently lacks:

Real route/path knowledge and stance costs (project uses geometric reference only).
Full strength evaluation that includes experience, bonuses, stances, and local context.
Recruitment feasibility and timing inside the same decision loop.
Local campaign context (threat maps, influence, exact movement extents) unavailable to the observer-safe snapshot.

Using v0.2G as an application allocator therefore risks systematically worse force selection: it can propose an exclusive, recovery-protected, anti-thrashing assignment that is geometrically attractive but path-infeasible, stance-illegal, or strength-misestimated relative to what the native system already knows. Explainability would improve; realized campaign performance could degrade. This is a concrete reason to keep v0.2G evaluator-only until native allocation quality is measured against the same metrics.
8. Deletion / demotion thresholds (achievable)

Demote v0.2F to evaluator-only if, after row-level reconciliation + controlled personality/task-generator ablations, native task sets under 8.1 already cover ≥90 % of critical fronts and recovery states on the project’s own challenge envelope across 10+ controlled late-game saves, with no systematic dropped-critical pattern.
Demote v0.2G to evaluator-only if native force-to-task allocation shows double-booking rate <5 %, recovering-army misuse rate below a pre-registered threshold, and thrashing (reassignment without material score gain) below the project’s own 4-turn/0.15-margin rate on the same saves.
Abandon v0.2I feasibility bridge if the above two demotions occur, or if live query results remain unavailable after one more bounded transport attempt and the upstream planner is no longer the decision source.
Adopt native CAI + bounded DB/script tuning as primary architecture if the evaluator metrics (coherent-rival persistence, recovery protection, thrashing, overcommit) are satisfied by tuned native under both vanilla and SFO profiles across the registered test set, and no fairness invariant is violated.

9. Reverse conclusion
Strongest case for “Transcendence should NOT own a strategic planner”:
Native CAI already performs the core loop (threat/strength → task generation → priority with distance/time/turn scaling → strength-ratio force selection → recruit-or-assign). Patch 8.1 and the 2025 betas demonstrably improved the exact late-game idling and anti-player problems that motivated the parallel stack. Major mods (DeepWar, Hecleas, Incata) already operate successfully by editing the exposed surfaces. The project’s distinctive machinery (exclusive slots, recovery gates, critical overflow, anti-thrashing) has no proven native equivalent but also has no proven necessity for good play; they can be metrics. Building a parallel planner risks both sunk-cost protection and performance degradation from poorer information (no real paths, incomplete strength, no recruitment loop). The high-value, low-risk role is evaluator + instrumentation + measured native tuning + fairness guardrails.
Strongest case against:
Native remains opaque on the exact decision that matters (which fronts are kept, which armies are protected, whether commitments thrash). Mod success is confounded with difficulty, budgets, and environment changes. Fairness, player-label invariance, SFO compatibility, and explainability are not native goals. If the evaluator repeatedly shows systematic recovery misuse, critical-front drops, or thrashing that cannot be fixed by the exposed tables, then a parallel planner becomes justified. The project’s contracts are the only currently existing specification of the desired behavior.
