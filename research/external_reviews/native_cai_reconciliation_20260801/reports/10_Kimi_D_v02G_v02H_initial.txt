5. WHAT SHOULD NEVER BECOME AN APPLICATION CONTROLLER WITHOUT FALSIFYING NATIVE CAI FIRST
The Euclidean assignment scorer (_candidate_record).
Native CAI already measures distance in turns with stance-aware movement extends. The project's hypot(dx, dy) / movement_points is strictly less informed than native distance scaling. To make this a controller, you would need to prove that native distance scaling is broken in a way that Euclidean geometry fixes — which is implausible on its face.
The severity-first greedy solver.
Native CAI has task generators → batching → allocation. The project's greedy solver ignores native task batching, native priority randomization, native personality weights, and native budget constraints. It cannot be justified as a controller without first demonstrating that native allocation systematically fails on observable metrics (idle armies, misallocated defenses, etc.).
Recovery protection as an assignment gate.
If native CAI already excludes recovering armies from task allocation (highly likely given the query system's mobile-asset filtering), then project-level recovery gating is redundant. It should remain an evaluator that checks whether native CAI respects recovery.
The reserve floor.
Native CAI has force-distribution managers and budget behaviors. There is no evidence that native CAI needs a hard reserve floor. Making this a controller would arbitrarily constrain native behavior without falsification.
Any mutation surface (cm:move_character, cm:attack, etc.).
The project correctly prohibits these. They should remain prohibited unless the entire architecture shifts to a replacement model (native CAI fully disabled), which the brief explicitly rejects: "prefer native WH3 capabilities and bounded correction before replacement."

7. MINIMAL ABLATION TEST
To determine which layers are actually adding information beyond native CAI, run the following ablation:
Test 1: Native-Only Baseline
Observe native CAI behavior for 20 turns with one controlled faction.
Record: task assignments, army movements, stance changes, idle turns.
Test 2: Shadow-Only (v0.2G output, no application)
Run v0.2G + v0.2F + v0.2E pipeline on the same scenarios.
Record: shadow assignments, candidate rankings, unfilled priorities.
Test 3: Divergence Analysis
For each turn, compare Test 1 vs Test 2.
Metrics:
Assignment agreement rate — same army → same target.
Severity agreement — does native prioritize CRITICAL when v0.2G does?
Reserve divergence — does native leave a reserve when v0.2G demands one?
Recovery violation rate — does native assign recovering armies to non-critical tasks?
Test 4: Feasibility Gate (v0.2H)
For each shadow assignment where Test 1 and Test 2 disagree, run v0.2H query plan.
Determine: was the native assignment feasible per v0.2H's query catalog? Was the shadow assignment feasible?
If native is feasible and shadow is not → shadow is wrong.
If shadow is feasible and native is not → potential native bug (flag for CA or mod fix).
Test 5: Temporal Commitment Calibration (v0.2G temporal)
With multi-army scenarios (synthetic or observed), measure native CAI's actual plan persistence.
Compare against v0.2G's 2/4-turn windows.
If native persistence is ~2–4 turns → v0.2G is descriptive, not prescriptive.
If native persistence is wildly different → v0.2G's windows are project fiction.
Decision rule: If Test 3 shows >80% agreement on critical priorities and Test 5 shows native persistence within ±1 turn of project windows, then v0.2G's assignment and commitment layers should be reframed as evaluators only. If agreement is <50%, there may be a genuine native CAI gap worth investigating — but even then, the fix should be native-first (table edits, personality tweaks, budget adjustments) before project-owned controllers.

Hypothesis: Maybe v0.2G's Euclidean assignment is better than native CAI.

If anything, the project should be querying POSITION_REACHABLE_THIS_TURN_IN_STANCE (v0.2H's documented query #8) rather than using Euclidean ETA.
